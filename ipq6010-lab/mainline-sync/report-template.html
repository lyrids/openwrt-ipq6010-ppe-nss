Image lineage and packages

The initial user-reported system was LibWrt25.12-SNAPSHOT/Linux6.12.108 on eMMC. Later custom RAM images introduced the open-source PPE/NSS stack, transactional Ethernet flow installation, VLAN and MTU guards, Wi-Fi flowtable lifecycle refresh, and persistent UDP socket defaults. Iteration11 updates the official OpenWrt base while retaining these effective changes.

The image does not require a package named kmod-qca-ppe-nss. PPE/EDMA belong to the target kernel driver layer; nss-wifi-drv is the community adapter, with separate firmware packages. A Linux6.18 version alone does not imply NSS firmware acceleration is integrated. Vendor qca-nss-drv and ECM are not used.

Datapath, acceleration and qdisc

Linux bridge / routing / conntrack / firewall
  ├─ Standard netfilter flowtable → qca_ppe / EDMA
  │    ├─ Native PPE Ethernet tables and schedulers
  │    └─ Community NSS Ethernet adapter → CP firmware
  └─ mac80211 / patched ath11k → community NSS Wi-Fi adapter
       └─ CP firmware Wi-Fi datapath / bridge and routed flows

PPE and NSS are distinct engines and interfaces. Disabling NSS does not automatically remove native PPE Ethernet acceleration. A physical LAN-to-LAN switch test alone cannot demonstrate NSS acceleration.

Queueing result and practical implication

Iteration 10 proved Ethernet TBF hardware caps: 100M yielded94.87Mbit/s and200M yielded188.28Mbit/s, versus936.53Mbit/s baseline. TC reported offloaded while NSS counters advanced. PRIO hardware attachment passed, but priority arbitration was not qualified.

On that image, Wi-Fi TBF/HTB/CAKE100M still forwarded837–849Mbit/s while Linux qdiscs counted only initial packets. Router-local Wi-Fi TBF100M did cap at95.68Mbit/s. This demonstrates NSS queue bypass, rather than invalid Linux queue setup. Current-image repetitions and NSS-off controls appear in the coverage table and measurements.

PPE's standard TC hook can program a physical Ethernet port shaper that also constrains NSS frames. The community Wi-Fi adapter does not thereby acquire firmware queue scheduling. A working Wi-Fi SQM design requires a verified host-path exclusion or a separately implemented TC-to-firmware scheduler interface.

Why this remains downstream maintenance

The community layer changes178 files at its original checkpoint, including PPE/EDMA, generic flowtable support, ath11k/mac80211, device-tree/clock support and the NSS adapter. The PPE-only control still contains this community-integrated PPE driver; it is not an unmodified official OpenWrt image. Standard Linux interfaces reduce coupling but do not make kernel APIs or the firmware ABI immutable. Future kernel updates still need source review, full rebuilds and hardware regression tests.

What the automation can and cannot recover

The p43 publisher verifies the expected SHA256 and FIT magic, saves a previous file and renames atomically. Normal TFTP boot is verified through gigabit LAN1. Failed-file and stopped-service fallback branches were previously exercised; a universally fixed fallback timeout was not established.

A kernel hang after control leaves U-Boot may require watchdog reset or physical recovery. TFTP fallback does not itself detect every post-boot Linux failure. Keep the independently saved iteration10 FIT available. USB fallback was discussed but has not been implemented or qualified.

On-demand U-Boot Telnet, HTTP recovery and UART

The installed bootloader was identified as2016.01-3011049 and matched to source commit3011049917bfb2fdc9a141196b3a94b63e58b96a. Existing network-abort support accepts UBOOT:ABORT on UDP37541 and acknowledges on37540. Its recovery loop provides Telnet23 when enabled. Normal boot continues after the5-second pause window when no request arrives.

Telnet is not continuously listening throughout autoboot and does not provide subsequent kernel serial output. SCREEN recovery uses the existing failsafe path. U-Boot's HTTP uploader and UART are distinct mechanisms; RAM loading versus flash-writing must be selected from the actual installed recovery implementation. No UART cable was available for these tests, and recovery-port behaviour should not be inferred from generic internet reports.

Kexec work was suspended after CPU restart/offline failures. The present images use normal U-Boot boots with kexec disabled; these failures are historical and are not presented as current NSS-off boot results.

Measurement method

Three controls

  1. NSS + PPE: NSS radio and Ethernet settings enabled, firmware booted, installed firmware flows/counters required.
  2. PPE / NSS off: same image sources, modules and packaged firmware, but host-path radio boot and Ethernet NSS disabled. Native PPE may still accelerate Ethernet.
  3. Software L3: NSS-off boot with both firewall software/hardware flow offload disabled. Physical LAN switching remains a hardware function.

Accounting

  • Receiver rate from iperf3 JSON; TCP saturation and matched100M UDP are compared by direction. Wired tests additionally include4 streams and300M UDP.
  • CPU comes from /proc/stat deltas during the active interval, omitting initial warm-up. Guest counters are not double-counted; idle and iowait are excluded from busy time.
  • Mean CPU uses total ticks across four cores. Softirq and maximum-core load are reported separately. Client/server CPU is retained to expose endpoint limits.
  • Monitoring and background work are included. CPU frequency uses schedutil rather than a fixed clock; these are busy-time percentages, not energy measurements. No CPU-cycle attribution, energy measurement or statistical confidence interval is claimed.

UDP uses1200-byte payloads and explicit4MiB socket requests (Linux actual8MiB buffers) consistently. Both routers retain8MiB send-default/send-max/receive-max profiles, with receive defaults unchanged. Profiles are persistent in WRT's UBIFS overlay and AX6600's custom TFTP images; the stock eMMC fallback is unchanged.

Firewall interpretation

Initial routing, conntrack and firewall decisions establish flows before acceleration. Offloaded packets then bypass parts of the normal per-packet path. New-connection deny tests, NAT address proof and bidirectional DNAT are distinct checks. A standard new deny rule is not claimed to revoke an already established connection accepted by an earlier state rule.

Using the results for configuration

  1. Compare matched100M UDP CPU and loss first; compare TCP saturation separately. A slower path doing less work is not automatically more efficient.
  2. If NSS and PPE-only both reach the1G endpoint ceiling, throughput cannot establish their maximum capacity. CPU cost and feature correctness remain useful.
  3. For Wi-Fi QoS, distinguish qdisc attachment from enforced shaping. Use the NSS-off shaping control to quantify the CPU/throughput trade-off before choosing SQM.
  4. Prefer the validated source/image checkpoint. Advance official OpenWrt first, package feeds separately, then the community/firmware layer so regressions are attributable.

Fast track for an experienced C/Linux developer

1 · Board and image contract

Read the target device definition, prepared device tree, partition labels, bootargs and FIT layout. Rebuild a baseline image, reproduce hashes/provenance, and RAM-boot with a tested rollback path before changing datapath code.

2 · Trace one packet and one rule

Trace netfilter/conntrack → flowtable → TC block → PPE/NSS adapter. Compare installed rules with firmware packet counters, PPE port/queue state and CPU/softirq deltas. Keep physical switch forwarding separate from routed or Wi-Fi forwarding.

3 · Driver and firmware boundaries

Study ath11k ring ownership, peer/vdev lifecycle, DMA mapping and NSS message layouts. Ethernet work belongs at the Linux/PPE flow-action boundary where possible; the NSS firmware ABI still needs explicit version handling and failure rollback.

4 · Make a narrowly scoped change

Use the source-derived transaction/MTU/VLAN regressions, compile the whole image and matching modules, then exercise fresh and established flows, peer movement, policy reload and unsupported-feature fallback. This qualification provides a repeatable hardware test template.

Limits, historical findings and evidence

Built-in 2.4 GHz: further retries were waived by the user after unsuccessful tests. Diagnostic results remain visible; this radio is not qualified.

  • QCN9074 is the external radio identified on this board. QCN9274/6GHz claims are not supported by the observed hardware.
  • The earlier QCN Wi-Fi upload concern was resolved by changing the faulty test client's adapter. Do not reclassify it as a confirmed router defect.
  • WRT's mwlwifi firmware stalled after an AP outage during iteration10 testing. Stopping the STA before DUT reboot is the recovery-avoidance procedure; client-side recovery incidents are recorded separately.
  • Historical buffer controls showed the WRT sender's small default budget restricted Wi-Fi UDP. Larger sender buffers restored throughput without a new NSS datapath patch. That finding does not identify the exact firmware queue/completion mechanism.
  • PRIO arbitration, RED/GRED congestion behaviour, ETS/MQPRIO semantics, arbitrary MTU hardware enforcement, USB boot and6GHz/2.5G capacity are not automatically qualified by the presence of code or modules.
  • The report and public evidence omit Wi-Fi keys and private configuration backups. Firmware binaries and credential-bearing backups stay outside Git.
